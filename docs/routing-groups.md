# 轮询组与随机选路

轮询组是多个通道实例组成的收款路由。业务应用可以绑定一个轮询组，发起**新的支付尝试**时，支付核心从组内可用成员中抽取一个通道。原来的单通道绑定继续兼容，升级不会自动创建轮询组或改派已有应用。

## 配置流程

1. 在「支付通道」创建收款账号，启用并完成当前配置版本的接口检测或实付验收。
2. 在「轮询组」创建组，添加一个或多个通道，选择规则并保存。
3. 在「业务应用」创建应用或修改列表中的「收款路由」，选择该轮询组。
4. 业务方继续使用原有 REST 或 ePay 接口。通常无需指定 `channel`，由绑定组选择通道。

组可以包含不同插件的通道，但请确保它们都适用于业务方的付款方式。不要将 Mock 模拟通道混入真实收款组；Mock 不代表真实资金到账。

## 选路规则

- **等概率随机 (`RANDOM`)**：每个可用成员具有相同概率。三条可用通道各约 1/3，不保证按顺序交替。
- **按权重随机 (`WEIGHTED_RANDOM`)**：只对可用成员的权重归一化。权重 1 和 3 的两条通道分别约为 25% 和 75%；若其中一条不可用，另一条为 100%。权重范围 1–10000，每组最多 100 个成员，同一通道不能重复加入。
- 成员可以单独暂停参与。通道停用、归档、当前配置未通过检测或成员暂停时不会进入候选集。
- 组停用或候选集为空时明确拒绝新支付，**不回退到旧默认通道或组外账号**。
- 保存组配置采用版本号保护；组规则和成员列表在同一事务内更新。

这不是顺序轮询、按成功率路由、自动故障切换或通道额度管理。抽签使用密码学安全的整数随机源，短期次数不保证严格符合比例。

## 支付安全与兼容性

- 支付单保存选中的 `channel`、`channelId` 以及选路来源快照 `routingGroupId`；创建事件还保存选路规则。
- 创建支付先锁业务订单，检查幂等键，再选路。创建事务使用 READ COMMITTED，显式订单行锁保护状态重读、幂等判断与尝试序号分配；选择后锁定通道并再次验证。
- 相同订单与 `Idempotency-Key` 返回原支付单，不重新抽签、不再次发起通道创建请求。组被停用、应用改派、绑定解除或订单成功/过期后，已有幂等支付仍可重放。
- 上游创建失败或结果不确定时，支付保留选中的通道，分别进入 FAILED/UNKNOWN。**不在同一次请求中自动换账号重试**，避免上游已创建但本地超时导致重复付款。
- 历史支付的回调验签、主动查单、关闭及退款始终通过支付单自身的通道绑定，不重新读取应用当前轮询组。
- 支付宝账单通道的金额预约、流水匹配与采集仍按被选中的 `channelId` 隔离。
- REST 请求中若显式提供 `channel`，它仅筛选组内对应插件，不能指定或访问组外通道。通常建议省略；ePay 对轮询组应用自动省略旧默认插件。
- 单通道和轮询组绑定互斥。切换到单通道会清除组绑定；切换到组会清除单通道绑定；解除绑定后，新支付会被拒绝。
- 仍有未归档应用绑定的组不能删除，包括已停用的应用。删除不影响历史支付来源快照。
- 删除未使用过的通道会移除对应成员；有资金历史的通道仍按原逻辑归档并被候选过滤。请留意组内剩余可用通道数量。

## 管理 API

以下接口均位于 `/admin/v1`，需要管理 Token。浏览器沿用 `/api/backend` BFF、管理员会话与同源写入保护。

| 方法 | 路径 | 用途 |
|---|---|---|
| GET | `/routing-groups` | 列表、可用成员数、绑定应用数 |
| POST | `/routing-groups` | 创建组 |
| POST | `/routing-groups/:id` | 更新组，必须携带当前 `revision` |
| POST | `/routing-groups/:id/delete` | 删除组，正文为 `{ "revision": 1 }` |
| POST | `/applications/:id/routing-group` | 绑定组 `{ "groupId": "组ID" }`，解除绑定时为 `null` |
| POST | `/applications` | 创建应用，可传 `routingGroupId`，不能同时传 `defaultChannelId` |

创建/更新示例：

```json
{
  "name": "支付宝主收款组",
  "strategy": "WEIGHTED_RANDOM",
  "enabled": true,
  "members": [
    { "channelId": "alipay-account-a", "weight": 1, "enabled": true },
    { "channelId": "alipay-account-b", "weight": 3, "enabled": true }
  ]
}
```

更新时增加 `revision`。列表仅返回通道摘要与验证状态，不返回通道密钥或加密配置。配置、删除和应用改派均沿用管理审计。

## 升级与验收

新增迁移：`202609300001_routing_groups`。新增两张组表及应用/支付的可空来源字段，不改动历史单据、账号配置或已有应用绑定。

生产升级前备份数据库并保留 `SECRETS_ENCRYPTION_KEY`。使用新镜像正常启动时，现有 Appliance 入口会执行 `prisma migrate deploy`；源码部署可执行：

```bash
npm run db:generate
npm run db:deploy
npm run build
```

不要让旧镜像与已升级的新 schema 长期混用。代码回滚时，旧镜像不会识别组绑定，组应用的 `defaultChannelId` 为空，无法创建新支付；必要时先把应用显式改回已检测的单通道。不要直接删除新字段或组表，以免丢失配置与历史来源线索。

### 自动化检查

```bash
npm run typecheck
npm test
npm run build
```

单元与接口测试覆盖随机整数区间、权重边界、配置验证、版本冲突、可用成员过滤、应用绑定/解除、管理员鉴权、ePay 接入、幂等复用以及上游失败不换账号。模拟数据库不能证明真实 MySQL 的行锁与并发行为。

### 测试环境验收（不在生产直接做）

1. 建立两个独立 Mock 通道并通过检测，创建组、绑定应用，确认新支付的 `channelId` 只出现在这两个账号中。
2. 用同一订单和相同幂等键并发发起多次支付，确认只有一个支付单与一次上游创建；不同键按既有多支付尝试模型处理。
3. 设置权重 1:3，以多个独立新订单观察抽样比例；小样本波动不视为失败。
4. 暂停成员、停用通道、修改配置使检测失效、归档通道，确认它们不再被新支付选中；全部不可用时返回 `ROUTING_GROUP_NO_CHANNEL`。
5. 停用组或解除应用绑定，确认新支付失败，但已有支付幂等重放、查单、回调和退款仍走原账号。
6. 并发修改组配置和创建支付，确认版本冲突被拒绝，没有半更新成员集合；观察 MySQL 锁等待与事务错误。
7. 在测试环境模拟上游创建超时，确认记录 UNKNOWN 且不尝试第二个账号。真实支付宝与账单收款按各通道原有实付验收手册执行。
