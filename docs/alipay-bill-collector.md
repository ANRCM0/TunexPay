# 支付宝账单独立采集器

## 订单驱动采集

内置 Worker 每 3 秒检查数据库是否有支付宝账单支付单需要采集；无需求时显示 `IDLE`，不请求支付宝。只有创建了 `ALIPAY_BILL` 支付单（不是仅创建业务订单）才会启动账单查询，查询间隔仍由面板控制，默认 10 秒。成功支付单不再驱动采集。

为发现延迟入库流水，未成功支付单在收款有效期结束后继续驱动一段补查期：`max(300, overlapSeconds + lagSeconds)` 秒，默认 315 秒。过期、关闭或失败单也纳入此短暂补查；窗口内流水仍按原匹配与异常处理规则处理，不会扩大支付有效期。补查期结束后停止请求。因此本采集器不再用于全天账单监控，补查期外的晚到账可能需要人工核对。

从空闲恢复时，将查询游标前移到最早仍需采集的支付单起始时间，再应用重叠覆盖；不再回查无订单的全部空闲时段。未完成的分页窗口保持原断点以支持重试。新支付单由下一次数据库检查发现；既有查询间隔、错误退避和其他 Worker 的租约仍有效，创建订单不会绕过限流或错误退避。当前页结束后重新检查需求，无需求则停止后续分页。

运行在现有 `worker` 服务中，仅调用 `alipay.data.bill.accountlog.query`，不依赖 MPAY 授权、浏览器、Cookie 或手机通知。请求 RSA2 加签；响应使用支付宝公钥校验原始响应对象的签名后才处理。

接口参考：https://opendocs.alipay.com/open/02awe0?ref=api

## 配置与升级

先备份数据库和当前配置，再将新代码部署到项目目录。不要删除数据库卷或变更已有 `SECRETS_ENCRYPTION_KEY`。

### 推荐：从面板配置（新增）

升级后进入“支付渠道 → 支付宝账单收款配置”，填写 App ID、2088 用户 ID、收款码、应用私钥和支付宝公钥，选择金额/备注模式（内置采集请选金额模式，原因见“查询与安全边界”），并启用“自动账单采集”和“账单收款”。保存后数据库配置生效，不需要重启容器。此处只配置账单通道，当面付通道仍沿用环境变量。

配置表在第一次访问或 Worker 启动时从 `.env` 导入一次。以后以数据库为准，改 `.env` 不会覆盖已保存的账单配置。首次配置不需要设置任何 `ALIPAY_BILL_*` 环境变量。服务器仍需通过 `.env` 配置数据库、Redis、管理员凭据、`SECRETS_ENCRYPTION_KEY`、公网 HTTPS 地址等基础设施参数。

私钥、公钥和外部令牌不会返回浏览器；页面只显示已配置状态。留空保留原值，“清除”才会删除。密钥支持 PEM 和 PKCS8 裸密钥；不提供证书模式。只有具有合法查询权限的账号才能真正拉取账单，保存成功不代表接口权限已验收。

“账单收款”控制接收新订单；“自动账单采集”可在停止新订单时继续运行。关闭采集在当前页结束后生效，已有流水仍会继续匹配。轮询频率、补拉参数、识别参数和密钥可热更新；有账单支付记录或采集断点后禁止直接换账号、网关或收款码。并发保存使用版本检查，冲突时重新加载配置。

请先检查 `WEB_PUBLIC_URL` 与浏览器实际 HTTPS 域名一致，否则面板保存会因来源校验拒绝。第一次升级仍需重新构建部署，之后修改账单配置才无需重启。

### 兼容：环境变量首次导入

```dotenv
ALIPAY_BILL_ENABLED=true
ALIPAY_BILL_COLLECTOR_ENABLED=true
ALIPAY_BILL_USER_ID=2088xxxxxxxxxxxx
ALIPAY_BILL_QR_CONTENT=收款码解析后的内容
ALIPAY_BILL_MATCH_MODE=AMOUNT
ALIPAY_BILL_POLL_SECONDS=10
ALIPAY_BILL_LOOKBACK_SECONDS=3600
ALIPAY_BILL_OVERLAP_SECONDS=300
ALIPAY_BILL_LAG_SECONDS=15
MOCK_CHANNEL_ENABLED=false
```

同时配置已验证具有账务查询权限的 `ALIPAY_APP_ID`、`ALIPAY_PRIVATE_KEY`、`ALIPAY_PUBLIC_KEY` 和 `ALIPAY_GATEWAY`，以及正确的 HTTPS `API_PUBLIC_URL`、`WEB_PUBLIC_URL`。密钥不得提交仓库；PEM 可写成带 `\n` 的单行值。

```bash
docker compose up -d --build api worker web
docker compose logs --tail 100 api worker
```

API 启动自动应用采集器及新增 `202609160007_bill_panel_settings` 迁移。代码更新需要重新构建。后台“支付渠道”可查看采集状态，再将应用默认渠道切为 `ALIPAY_BILL`，使用新订单测试。

内置采集直接调用本地支付服务，不需要 Watcher 令牌。没有配置外部令牌时，外部流水 HTTP 入口仍拒绝请求。兼容外部 Watcher 时继续设置至少 24 字符的专用令牌。

## 查询与安全边界

- 单账号 `alipay-bill-default`，二维码必须属于配置的查询账号。
- 首次采集从最早需要采集的支付单起始时间建立断点；后续从断点继续或跳过空闲历史。订单驱动模式不使用首次回查时长参数。每个窗口最多前进 30 分钟，默认回叠五分钟，最新数据延后 15 秒查询。
- 每轮最多五页，每页 100 条。固定窗口和页码持久化，下轮继续未完成窗口。
- 接口字段契约（已对真实生产账号验签响应核实）：列表字段为 `detail_list`（空窗口整个省略），条目使用 `direction`（收入/支出）、带符号 `trans_amount`、`alipay_order_no`、`trans_dt`、`merchant_order_no?`、`type?`、`account_log_id`。**接口不下发付款备注**，因此内置采集器只能使用金额（AMOUNT）匹配；备注（REMARK）匹配仅适用于能抓到备注的外部 Watcher 或日账单 CSV。未知结构报错并保留断点，不能当作“没有收入”。
- `direction === "收入"` 且 `trans_amount` 为正、有支付宝订单号的条目才送入匹配；明确退款/冲正类型的条目排除。账务明细并非全部是顾客付款，仍需业务金额、时间和有效期校验。条目入账时间不必然等于原始交易付款时间，也需联调检查延迟。
- 流水先持久化，再推进页码；失败重放，交易号去重和支付核心幂等防止重复充值。
- 查询失败指数退避，最多五分钟；多 Worker 使用数据库租约。Compose 给 Worker 120 秒优雅退出时间。
- 后台显示心跳、成功查询时间、断点、页码和错误码。`RUNNING` 不代表所有真实支付场景已验收。
- App ID、用户 ID、网关或二维码变更时暂停采集，显示 `ACCOUNT_BINDING_CHANGED`。需人工核对未完成订单并迁移账号，不要直接清空状态表复用历史订单。
- 回叠补拉不能覆盖超过配置时间的延迟入账。需观察实际延迟、调整回叠时间，并保留日终账单或人工对账兜底。
- 静态码不能由系统真正关停；退款仍需人工处理。金额模式中普通同额转账可能误配，应隔离日常转账和业务收款；备注模式更精确，但只对提供备注的外部 Watcher 有效（官方账务接口无备注字段）。

## 真实上线验收（尚需账号执行）

1. 使用独立测试应用，暂不连接正式充值业务。确认查询成功，日志没有权限/验签错误。
2. 小额实付（金额模式按预约尾数付款），核对实收金额、时间、支付宝交易号和订单状态。若使用外部 Watcher 备注模式，再验证备注完整到达。
3. 验证重叠查询不重复充值，重启 Worker 保留断点，暂时断网恢复后补拉。
4. 验证错付、金额不符、过期和多候选不自动充值。
5. 最后连接 NewAPI，确认通知送达且只充值一次，配置备份和定期对账。

本地模拟接口测试不是支付宝真实账号验收。未验证真实字段和收入场景覆盖前，不开放无人值守生产充值。
